# ML Handoff — connecting the AI/ML FastAPI service to FieldVerse

**Audience:** the AI/ML team building the Python FastAPI analysis service.
**Goal:** connecting your service should only need configuration and fixing real schema differences. The React app and the Express API should not need changes.

> Status: the contract below is **proposed by the SE team** (schema version `1.0`). Items marked **⚠ To confirm** need agreement between the two teams. Nothing in FieldVerse assumes your service already matches this contract.

---

## 1. How the pieces connect

```
Browser (React)  ──►  Express API  ──►  AnalysisProvider
                       /api/v1          ├─ DemoAnalysisAdapter  (ANALYSIS_PROVIDER=demo)   ← today
                                        └─ HttpAnalysisAdapter  (ANALYSIS_PROVIDER=remote) ──► your FastAPI
```

- The browser **never** calls your service directly. Express validates every request before forwarding it, then validates every response you return (`apps/api/src/adapters/analysis/HttpAnalysisAdapter.ts`).
- A response that does not match the contract is **rejected** with `ANALYSIS_BAD_RESPONSE`. It is never shown to farmers.
- If your service is down, Express returns an explicit error. The UI may *offer* the farmer a clearly labelled demo result instead, but it never switches silently.

The single source of truth is the Zod schemas in [`packages/contracts/analysis/`](../packages/contracts/analysis/):

| File | Contains |
|---|---|
| `common.ts` | `SCHEMA_VERSION`, `SourceType`, `Interval`, `SourceRef`, `MeasuredValue` |
| `environment.ts` | `EnvironmentSummary` (climate, annual, soil layers, NDVI, media) |
| `requests.ts` | `RotationComparisonRequest`, `ClimateScenarioRequest`, `GapAnalysisRequest`, `FarmerConstraint` |
| `responses.ts` | `Strategy`, `RotationComparisonResponse`, `ClimateScenarioResponse`, `GapAnalysisResponse`, `ModelInfo`, `AnalysisErrorBody` |
| `examples/*.json` | Example requests, plus example responses generated by the demo adapter |
| `json-schema/*.json` | JSON Schema export, generated by `npm run contracts:jsonschema` |

**Using the schemas from Python:** run `npm run contracts:jsonschema`, then generate Pydantic models, for example:

```bash
pip install datamodel-code-generator
datamodel-codegen --input packages/contracts/analysis/json-schema/rotation-comparison.response.schema.json \
                  --input-file-type jsonschema --output models/rotation_comparison_response.py
```

## 2. Endpoints your FastAPI service should expose

| Method | Path | Request body | Success response (HTTP 200) |
|---|---|---|---|
| GET | `/v1/model-info` | – | `ModelInfo` |
| POST | `/v1/rotations/compare` | `RotationComparisonRequest` | `RotationComparisonResponse` |
| POST | `/v1/scenarios/analyze` | `ClimateScenarioRequest` | `ClimateScenarioResponse` |
| POST | `/v1/gaps/analyze` | `GapAnalysisRequest` | `GapAnalysisResponse` |

- Content type is `application/json` for all of them.
- Optional auth: if `ML_SERVICE_API_KEY` is set, Express sends `Authorization: Bearer <key>`.
- These paths are defined once, in `ML_ENDPOINTS` in `HttpAnalysisAdapter.ts`. **⚠ To confirm:** the paths and the `/v1` prefix.

## 3. Requests

All requests carry `schemaVersion: "1.0"`. Express has already validated them, applied defaults and normalised them.

### 3.1 `RotationComparisonRequest`

```jsonc
{
  "schemaVersion": "1.0",
  "regionId": "sri-lanka-anuradhapura",      // slug, see §6
  "field": {
    "latitude": 8.3114, "longitude": 80.4037, // WGS84 decimal degrees
    "currentCrop": "rice",                    // crop id, see §7
    "cropHistory": ["rice", "rice"],          // most recent first, may be []
    "soilType": "unknown",                    // clay | loam | sandy | silt | unknown
    "soilPh": null,                           // farmer's soil test, 3–10, or null
    "irrigation": "limited",                  // none | limited | full | unknown
    "areaHectares": null                      // optional
  },
  "priorities": { "water": 0.4, "soilHealth": 0.3, "risk": 0.2, "income": 0.1, "idleLand": 0 },
  "scenario": { "rainfallChangePercent": 0, "temperatureChangeCelsius": 0 },
  "constraints": [],                          // Farmer's Right to Disagree, see §3.4
  "locale": "en"                              // language for human-readable text
}
```

- **Priorities** are relative importance weights, each from 0 to 1. They are not guaranteed to sum to 1, so normalise them if your method needs that.
- **"unknown" means the farmer did not know.** Do not treat it as a value.

### 3.1a Farmer input form → contract fields

The farmer form follows *Roots of Tomorrow: Farmer Input Form Specification* (Nov 14, 2026). Its snake_case keys map to the camelCase contract fields as follows. "I do not know" is always sent as `null` or `"unknown"`, never guessed.

| Spec key | Contract field | Values |
|---|---|---|
| `location` | `field.latitude`, `field.longitude` | WGS84 decimal degrees |
| `current_crop` | `field.currentCrop` | crop id, `"fallow"`, or a farmer-added slug ("Other") |
| `harvest_month` | `field.harvestMonth` | 1–12, `"harvested"`, or `null` |
| `previous_crop`, `previous_crop_2` | `field.cropHistory[0]`, `[1]` | crop id or `"fallow"`; seasons the farmer does not remember are omitted |
| `next_planting_month` | `field.nextPlantingMonth` | 1–12, or `null` ("I am not sure" → estimate from local rainfall) |
| `seasons_per_year` | `field.seasonsPerYear` | 1, 2, 3, or `null` |
| `water_access` | `field.irrigation` | `none` (rainfall only), `limited`, `full`, `unknown` |
| `waterlogging` | `field.waterlogging` | `several_weeks`, `few_days`, `drains_well`, `unknown` |
| `input_level` | `field.inputLevel` | `minimal`, `moderate`, `high`, `unknown` |
| `soil_texture` | `field.soilType` | `clay`, `loam`, `sandy`, `silt`, `unknown` |
| `soil_ph` | `field.soilPh` | 3.0–10.0, or `null` |
| `excluded_crops` | `field.excludedCrops` | crop ids. These must be **removed** from candidates; report them with `constraintFlags[].constraintType = "excluded_crop"`. |
| `priorities.water_saving` … `food_security` | `priorities.water`, `soilHealth`, `risk`, `income`, `idleLand` (= `fallow_use`), `foodSecurity` | 0–1 weights (the UI maps Not / Slightly / Important / Very important to 0, ⅓, ⅔, 1, then normalises). Ordering only. |

The demo adapter applies only `excludedCrops`, `irrigation = none` and `waterlogging = several_weeks`, through documented rules. It lists any other answers it could not use in `limitations`. **⚠ To confirm:** how the "Moderate" input level maps to GAEZ layers (the specification proposes a range between low and high input), and the final crop list (wetland vs. dryland rice).

### 3.2 `ClimateScenarioRequest`

This is the same as the comparison request with a required `scenario` and an optional `baselineRequestId`.

- `rainfallChangePercent` must be between −50 and +50. It is applied to every month relative to the observed baseline.
- `temperatureChangeCelsius` must be between −2 and +5.
- Scenarios are hypothetical "what if" assumptions, not forecasts.
- If your model supports only some combinations, set `capabilities.scenarioInput: "presets"` and list them in `scenarioPresets`. For anything else, return `SCENARIO_NOT_SUPPORTED`.

### 3.3 `GapAnalysisRequest`

```json
{ "schemaVersion": "1.0", "regionId": "kenya-nakuru", "field": { "...": "..." }, "idleMonths": [9,10,11,12,1,2], "locale": "en" }
```

`idleMonths` are months from 1 to 12 that the farmer marked as having no crop. Windows can wrap across the year, for example December to February.

### 3.4 Farmer constraints

| `type` | `cropId` | Meaning |
|---|---|---|
| `no_irrigation` | – | The farmer has no irrigation |
| `seeds_unavailable` | **required** | Seed for that crop cannot be obtained |
| `soil_floods` | – | The field often waterlogs |
| `cannot_sell` | **required** | No local market for that crop |
| `lacks_equipment` | – | Missing suitable equipment |
| `crop_failed_before` | **required** | That crop failed on this land before |

Each item can also carry an optional free-text `note` of up to 280 characters.

For every constraint, return an entry in `constraintsApplied` that says what you actually did:

- `"handling": "model"` — your model recalculated with this constraint.
- `"handling": "rule"` — you applied a simple filter or flag.
- `"handling": "not_supported"` — you did not assess it.

The UI shows this to the farmer word for word, so never claim more than was done.

## 4. Responses

Every analysis response includes these fields:

| Field | Type | Rule |
|---|---|---|
| `schemaVersion` | `"1.0"` | |
| `requestId` | string | Unique per response |
| `mode` | `"remote"` | **Must** be `remote`. Express rejects any other value. |
| `modelVersion` | string | Your real model version, e.g. `"fv-rotation-0.3.1"` |
| `region` | `RegionSummary` | |
| `limitations` | string[] | Plain-language limits of this result |
| `dataSources` | `SourceRef[]` | Every source referenced by `sourceId` or `sourceIds` |
| `disclaimer` | string | Short notice shown prominently |
| `generatedAt` | ISO-8601 datetime | |

### 4.1 `Strategy` (one rotation option)

| Field | Notes |
|---|---|
| `id`, `name`, `kind` | `kind` is `current` or `alternative`. Return exactly one `current` (the farmer's present rotation) and up to 5 alternatives. **⚠ To confirm:** the UI is designed for 3 in total. |
| `summary` | One plain-language sentence |
| `steps[]` | Ordered crops: `cropId` (or `"fallow"`), `role` (`main`, `short_season`, `cover` or `fallow`), `season {name, startMonth, endMonth}`, optional `plantingWindow` |
| `feasibility` | `status` is `feasible`, `needs_review`, `not_feasible` or `unknown`, plus `reasons[]` |
| `suitability` | `level` is `low`, `medium`, `high` or `unknown`. `score` (0–100) or `null`. `scoreType` is `"model"`. `interval` is optional. |
| `indicators[]` | 1–5 ratings with a `direction`. Use these ids where possible: `water_demand`, `soil_cover`, `nitrogen_contribution`, `climate_risk`, `income_opportunity`. Set `ratingType: "model"`. |
| `water`, `soilCover` | Relative water demand and months of soil cover, with notes |
| `benefits[]`, `risks[]` | Each with a `sourceType`. Risks also carry a `severity`. |
| `explanation` | `summary`, `details[]`, optional `technical` |
| `dataGaps[]`, `localChecks[]` | What is missing, and what the farmer should check locally |
| `uncertainty` | `level`, `notes`, optional `interval` |
| `constraintFlags[]` | How the farmer's constraints affected this strategy |
| `priorityFit` | Optional: `{rank, method: "model", explanation}` |
| `sourceIds[]` | Ids from `dataSources` |

### 4.2 `ClimateScenarioResponse` adds:

- `baseline` and `modified`: the applied scenario, each with a `label`.
- `climateContext`: baseline and hypothetical annual rain and mean temperature, plus a `note`.
- `changes[]`: per strategy, `direction` (`improves`, `worsens`, `unchanged` or `unknown`), `feasibilityBefore`, `feasibilityAfter` and `summary`.
- `explanation[]`.

### 4.3 `GapAnalysisResponse` adds:

- `currentCalendar[]`
- `idleWindows[]`, which includes the window's rainfall
- `candidates[]`: crop, `role`, `windowIndex`, `durationDays`, `fit` (`fits`, `tight`, `does_not_fit` or `unknown`) and `fitMethod` (`"model"`)

Complete examples are in `packages/contracts/analysis/examples/`. Today they are generated by the demo adapter, so their `mode` is `demo`; your service returns `remote`.

| Quantity | Unit |

## 6. Supported region identifiers (today)

| `regionId` | Name | Centre (lat, lon) | Demo radius |
|---|---|---|---|
| `sri-lanka-anuradhapura` | Anuradhapura, Sri Lanka | 8.3114, 80.4037 | 60 km |
| `kenya-nakuru` | Nakuru County (near Njoro), Kenya | −0.33, 35.94 | 50 km |
| `brazil-mato-grosso` | Sorriso, Mato Grosso, Brazil | −12.5425, −55.7211 | 80 km |

**Farms anywhere in the world** use `regionId: "custom"` together with their real `latitude` and `longitude`. The demo provider refuses these with `REGION_NOT_SUPPORTED`, because it has no prepared examples. Your service may support them. Crop ids may also be farmer-added slugs that are not in the catalogue (for example `cassava`); return `CROP_NOT_SUPPORTED` if your model cannot handle them.

Report the regions you actually support in `ModelInfo.supportedRegions`. **⚠ To confirm:** whether your service accepts any coordinate or only these regions.

## 7. Crop identifiers

`rice`, `maize`, `mung-bean`, `cowpea`, `common-bean`, `sorghum`, `soybean`, `sunn-hemp`, `lablab`, plus the special step value `fallow`. These are defined in [`data/demo/crops.json`](../data/demo/crops.json).

Identifiers are lowercase slugs and are never translated. If you add crops, send their ids; the UI shows a fallback tile. Tell the SE team so we can add illustrations.

## 8. Errors

For any non-2xx response, return this body:

```json
{ "error": { "code": "SCENARIO_NOT_SUPPORTED", "message": "Plain-language explanation", "details": {} } }
```

| Your code | HTTP | Express maps it to |
|---|---|---|
| `VALIDATION_ERROR` | 400 or 422 | `VALIDATION_ERROR` (400) |
| `REGION_NOT_SUPPORTED` | 422 | `REGION_NOT_SUPPORTED` (422) |
| `CROP_NOT_SUPPORTED` | 422 | `CROP_NOT_SUPPORTED` (422) |
| `SCENARIO_NOT_SUPPORTED` | 422 | `SCENARIO_NOT_SUPPORTED` (422) |
| `DATA_UNAVAILABLE` | 422 | `DATA_UNAVAILABLE` (422) |
| `MODEL_NOT_READY` | 503 | `ANALYSIS_UNAVAILABLE` (503) |
| `INTERNAL_ERROR` | 500 | `ANALYSIS_UNAVAILABLE` (503) |

Express handles these failures on your behalf:

- Timeouts (`ML_SERVICE_TIMEOUT_MS`, default 15 s) become `ANALYSIS_TIMEOUT` (504).
- An unreachable service becomes `ANALYSIS_UNAVAILABLE` (503).
- Non-JSON or contract-violating responses become `ANALYSIS_BAD_RESPONSE` (502).

## 9. Provenance requirements

Every measurement and result carries a `sourceType`:

| Value | Use for |
|---|---|
| `observed` | Satellite, reanalysis or station observations (NASA POWER, MODIS…) |
| `estimated` | Global model products such as SoilGrids, and general reference ranges |
| `farmer_provided` | Values the farmer entered |
| `modelled` | **Your model's outputs** |
| `demo` | Prepared illustrative content. Must not appear in remote responses. |
| `unavailable` | No data |

Every `sourceId` or `sourceIds` entry must resolve to an item in `dataSources`, with `name`, `provider`, `datasetVersion`, `spatialResolution`, `temporalCoverage`, `url`, `retrievedAt` and `license` where known.

## 10. Uncertainty

- `interval` fields are **optional**. Send `{lower, upper, level, method}` only when your method really produces them. **Never invent intervals.**
- `uncertainty.level` (`low`, `medium`, `high` or `unknown`) and `uncertainty.notes` are always required. `unknown` is a valid, honest answer.
- Do not send accuracy percentages unless they come from a documented validation, and explain that validation in `ModelInfo.trainingDataSummary`.

## 11. Model status metadata (`GET /v1/model-info`)

```json
{
  "schemaVersion": "1.0",
  "provider": "remote",
  "name": "FieldVerse rotation model",
  "modelVersion": "fv-rotation-0.1.0",
  "status": "ready",
  "capabilities": { "rotationComparison": true, "climateScenario": true, "gapAnalysis": false, "constraints": "model", "scenarioInput": "continuous" },
  "supportedRegions": ["sri-lanka-anuradhapura"],
  "supportedCrops": ["rice", "mung-bean"],
  "scenarioPresets": [],
  "trainingDataSummary": "…datasets, periods, validation…",
  "lastUpdated": "2026-11-20",
  "notes": null
}
```

The UI reads `capabilities.scenarioInput`:

- `"continuous"` — the Climate Time Machine sends any slider value.
- `"presets"` — it sends only the listed `scenarioPresets` and explains anything else.

## 13. Switching from DemoAnalysisAdapter to HttpAnalysisAdapter

1. Start your service, for example `uvicorn app:app --port 8000`.
2. Verify compatibility (§14).
3. In `.env`, set `ANALYSIS_PROVIDER=remote` and `ML_SERVICE_URL=http://localhost:8000`.
4. Restart the API with `npm run dev:api`.
5. Check `GET /api/v1/analysis/status`. It should report `provider: "remote"`, `status: "ready"` and your `modelVersion`.
6. Open the Rotation Lab. The amber "Illustrative demo" notice is replaced by the dark "Live analysis (model …)" notice.

No React or Express code changes are needed. If a real schema difference shows up, fix it in your service or agree a contract change. Contract changes are made in `packages/contracts` and the version number is bumped.

## 14. Contract tests

```bash
# 1. Check your running service against the example requests and the Zod contract
ML_SERVICE_URL=http://localhost:8000 npm run verify:ml

# 2. Contract unit tests (example fixtures + rules)
npm run test -w @fieldverse/contracts

# 3. Regenerate example responses / JSON Schema after a contract change
npm run examples -w @fieldverse/api
npm run contracts:jsonschema
```

`verify:ml` exits with code 0 when every endpoint returns contract-valid data and the error format is correct. Otherwise it prints each failing path and message.
